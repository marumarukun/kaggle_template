# Engineering Notes

> モデル性能の良し悪しではなく、複数の実験に影響する実装・運用上の注意事項だけを残す。

## Experiment Execution

- ローカルでのPython実行には `uv run python` を使う。
- 学習時は `EXP_VERSION=next` を指定し、既存の成果物を上書きしない。
- スコア記録後の実験コードは原則固定し、条件変更は新しい実験番号で行う。
- 別実験の `config` を `sys.path` の変更でimportしない。モジュール衝突や出力先の取り違えにつながる。

## Training / Inference Consistency

- 学習と推論で、特徴量、前処理、列順、モデル設定が一致していることを提出前に確認する。
- 推論で読み込む実験番号と、アップロードしたartifactの実験番号・versionを一致させる。

## Kaggle Submission

- codeとmodel artifactは対応する組み合わせでpushする。
- `model_sources` にはKaggle上の最新model versionだけを指定できる。ローカルのversion番号とKaggleのversion番号を混同しない。

### Notebook手動実行

- ログ・print出力を確認できるため、提出前の動作確認と原因調査に使う。
- 手動実行で使われるのは公開されたsample/pseudo testであり、本番のhidden testではない。
- hidden testはデータ量、値の分布、欠損や未知値などのエッジケースが異なり得る。手動実行が成功しても、実提出が成功するとは限らない。

### コンペへの実提出

- 非公開のhidden testで再実行されるが、そのログ・print出力は一切確認できない。成功/失敗などの状態だけが観測可能。
- 実提出ERRORの調査を目的にログやprintを追加しても確認できないため、その提案・実装をしない。
- 例外を握りつぶす処理、定数予測、sample submissionの流用、失敗行のスキップ、代替モデルなど、ユーザーが意図しないフォールバックを入れない。
- 想定外の状態ではfail fastにし、原因はローカルまたはNotebook手動実行で再現する。hidden testとの差を想定した入力規模・値・欠損・エッジケース・時間・メモリ条件も検証する。
- 再現できない原因を断定せず、根拠のない修正で提出コードの挙動を変えない。

## Maintenance Policy

- この文書へ追加するのは、複数実験に影響し、再発すると結果や提出を壊す、現在も有効な事実だけにする。
- 特定手法の性能評価、アイデア、実験固有のメモは記載しない。
- 注意事項が不要になった場合は履歴として残さず、削除または現在の仕様に書き換える。
